# 千刀插件设计

目标是把原来 Codex Desktop、CCS 直连配置和千刀网关配合使用的效果迁入 Magpie：Codex 发起请求，千刀插件管理并发、消化可恢复错误，成功后再交付回答。旧网关的实际行为是对照基准。

交付单位是一个 Magpie 插件。模型转发、错误恢复、并发调度和设置均集成在插件内，运行生命周期归 Magpie 宿主管理。

## 请求路径

插件在 Magpie 中注册独立的“千刀网关”供应商，采用与 AG 网关插件相同的选择方式。用户选择新供应商下的模型后，请求进入千刀插件；原有普通千刀供应商独立存在。

Codex → Magpie 的千刀 Provider → 千刀服务。中间件仅关联同一次请求的宿主调用，插件移除内部关联信息后再发往用户填写的 Base URL。一次请求使用同一地址和凭据；模型、推理强度、服务等级、会话与缓存字段保持原有语义。

请求体和工具调用历史不因限流而裁剪或修复。模型列表不可用时仍允许使用手填模型。API Key 由 Magpie 保存。

## Fast 模式

Fast 必须能直接在 Magpie 中启用。优先使用模型选择器每行右侧的原生闪电开关；宿主无法为插件模型提供该入口时，在“千刀网关”供应商设置中提供 Fast 开关。采用一个明确的控制入口。用户在 Magpie 开启后，即使 Codex 请求没有主动携带 Fast 参数，上游请求也使用 `service_tier: "priority"`。关闭时按普通模式处理，不因先前选择残留强制 Priority；重试保持本次请求已确定的服务等级。

插件为对应模型声明 `priority` 服务等级和正确的 Responses 协议，使 Magpie 能识别并应用 Fast。推理强度按用户选择保留，插件不因开启 Fast 而改写推理档位。

验收从实际交付的 Magpie Fast 开关入口开始：Codex 请求不带 `service_tier`，开启后模拟上游收到 `priority`；关闭后不再被强制为 `priority`；重试保留同一选择。内置模型与用户手填的受支持模型均覆盖，并检查上游返回的实际服务等级是否保留。

## 错误恢复

完整缓存一次上游响应，按照旧网关规则判断是否可交付。可恢复错误和交付前断流在插件内等待后重试；不把失败尝试的部分回答或工具调用交给 Codex。

默认最多 7 次上游尝试，含首次；300 秒内准入新尝试，单次上游请求最长 900 秒。限流等待为 3、6、10、20、40、60 秒，普通错误等待为 0.75、1.5、3、3、3、3 秒。每次请求首次遇到大于 30 秒的有效 `Retry-After` 时，先等 30 秒重试一次；之后取上游当前等待时间与原退避时间中的较大值，不再重复缩短。已有的更长共享冷却不缩短，次数与期限不延长。同一次客户端请求被 Magpie 重复调用时共用已有预算，耗尽后不再向千刀发送。

明确的上下文超限、鉴权失败及其他不能靠重复同一请求恢复的终态，保留错误语义交付。`response.failed` 应先解析错误原因：`context_length_exceeded` 保留响应事件，让 Codex 有机会自动压缩；临时限流或繁忙仍可在内部重试。错误语义不明确时，仅凭笼统的“额度”字样不判定永久失败。

每次客户端请求固定首次实际上游发送的正文、地址、凭据、Fast 选择和必要请求头，并保存预算及最终结果。宿主再次调用同一请求时，沿用这些状态；已有不可恢复终态或预算耗尽时直接交付对应结果，避免宿主删改参数后继续发送造成 Fast 降级或改变会话语义。

旧实现的行为依据见 [旧网关行为](research/qiandao-behavior.md)。客户端取消时终止等待和上游请求；客户端主动重发或自动重连属于新的请求，但仍受共用冷却与并发约束。

## 并发与设置

整个插件共用一个上游并发池，初始 5；多个对话、模型和账号合计受该上限约束。排队与等待退避不占正在向千刀发送请求的名额。并发提高后允许更多请求进入；调低时已有请求继续，后续等待到在途数量低于新上限再进入。

使用官方插件页面服务提供“千刀地址”和“总并发”表单，设置持久化后更新当前插件状态，不通过重载共享插件宿主来应用这些值。页面服务仅承载设置，模型请求始终通过 Provider 直接发送到千刀。地址更改用于之后进入的新请求，在途请求及其重试继续使用原地址；修改不要求重新填写聊天 Key。

并发名额、排队顺序与冷却时间通过插件数据目录共享，覆盖新旧宿主短暂并存的请求。数据仅记录调度信息，进程退出后回收其名额。设置页使用固定的本机端口；宿主重载期间沿用仍存活的页面服务，新宿主在端口释放后接管。

## 接入验收

以本地模拟千刀对照新旧网关，检查实际发送次数、请求内容和 Codex 可见结果，覆盖正常响应、429、200 内嵌错误、部分内容后断流、永久错误、取消与预算耗尽。再用打包后的插件和当前真实 Magpie 宿主验证登录、手填模型、参数透传、地址修改、多账号共用并发和宿主重复调用。

上下文超限验收应确认 Codex 最终收到正确的 `response.failed` 错误语义；鉴权失败不因宿主再次调用而重新打上游。Fast 被明确拒绝时不静默改为普通模式重新发送。宿主重载期间的在途请求与并发状态需要单独验证，日常设置保存不得通过重载来应用。

## 客户端与配置范围

Codex 保持默认等待设置。千刀插件的安装和参数调整限于本插件，不修改 Codex 或 Magpie 的全局配置，也不改变其他供应商的超时、重试或并发设置。客户端因超时关闭连接或主动取消时，插件终止当前请求的排队、退避和上游调用。

## 已知限制

完整缓存不逐字显示内容，失败尝试已消耗的上游计算不能撤回。默认客户端等待期限可能早于网关预算结束，因此长时间没有内容的请求可能先在 Codex 超时；不保证旧网关最长等待窗口全部可用。Magpie 仍可处理插件最终错误，共享预算约束的是实际向千刀发送的次数。客户端重新发起请求拥有新预算。千刀内部路由、缓存命中以及是否认可插件接入由上游决定。
